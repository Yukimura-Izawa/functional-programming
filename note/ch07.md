# 07 型としての要件

## 概要

6章は「失敗したら値で返す」。7章は「失敗の原因になるデータを、最初から作らせない」

不正なデータを、そもそも作れないように、要件を型で表す

### 身につけるべきこと

- 7.1 newtype：同じ中身の値を区別する
- 7.2 Algebraic Data Type（代数的データ型, ADT）：「かつ」と「または」で、矛盾した状態を作れなくする
- 7.3 パターンマッチ：ADT を使う関数を書く
- 7.4 振る舞いもデータで表す

### 詳細

- name も origin も String だと、引数を入れ替えてもコンパイラが気づけない。中身は String のままで、別の型として扱えるようにする
- 直積型（かつ）：全部の項目を持つ。case class、Rust の struct
- 直和型（または）：どれか1つ。enum、Rust の enum
- 「ないかもしれない」を表す Option も、直和型の1つ
- 直和型の値は、どのケースかで分岐して中身を取り出して使う。ケースを書き忘れたり型を変えたりすると、コンパイラが直す場所を教えてくれる
- 「ジャンルで検索」「出身地で検索」のような検索条件そのものを直和型にして、関数の引数として受け取る

### 流れ

```
String や Int だけだと不正なデータが作れる
→ 7.1 newtype で取り違えを防ぐ
→ 7.2 ADT で矛盾した組み合わせを防ぐ
→ 7.3 パターンマッチで ADT を安全に使う
→ 7.4 振る舞いも ADT で表す
```

### まとめ

1. newtype：中身が同じ型でも別の型にして、取り違えを防ぐ
2. ADT：直積（struct：全部持つ）と直和（enum：どれか1つ）を組み合わせて、矛盾したデータを作れなくする
   - 例：活動期間 = 「今も活動中（開始年）」か「活動終了（開始年と終了年）」
3. パターンマッチ：どのケースかで分けて中身を取り出す。書き忘れはコンパイラが教えてくれる
4. 振る舞いもデータに：検索条件を enum にして、match で処理する（全部満たすかは all）

## 7.1 newtype：同じ中身の値を区別する

### ゴール

String や Int だけで作ったデータの何が危ないかを説明でき、newtype で取り違えを防げること

### 詳細

音楽アーティストを検索する例

```scala
case class Artist(
  name: String,
  genre: String,
  origin: String,       // 出身地
  yearsActiveStart: Int,
  isActive: Boolean,
  yearsActiveEnd: Int
)
```

これはジャンルと出身地を逆に渡しても、エラーにならない。
→ どちらも String なので、コンパイラには区別がつかないから。

#### 解決策：newtype で別の型にする

newtype：中身は同じでも、名前の違う別の型として扱うしくみ

```scala
object model {
  opaque type Location = String               // ①中身は String だが、別の型

  object Location {
    def apply(value: String): Location = value              // ②作るための関数
    extension (a: Location) def name: String = a            // ③中身を取り出すための関数
  }
}
```

それぞれの役割は次のとおり

1. `opaque type Location = String`：model の中では「Location は String と同じ」と分かる。しかし外からは、String とは別の型にしか見えない。
2. `apply`：`Location("U.S.")` と書いて Location を作るための関数。中身が String だと分かっている model の中で定義するので、String をそのまま Location として返せる。
3. `extension ... def name`：`location.name` と書いて、中身の String を取り出すための関数

これを用いて Artist を書けば、

```scala
case class Artist(name: String, genre: String, origin: Location, ...)
Artist("Metallica", "Heavy Metal", Location("U.S."), ...)   // 正しい
Artist("Metallica", Location("U.S."), "Heavy Metal", ...)   // コンパイルエラー
```

#### 注意

ここでやっているのはあくまで、値に「これは場所です」というラベル（型）を貼るしくみ。
つまり、間違った中身にラベルを貼ることは防げない

```scala
Artist("Metallica", "Heavy Metal", "U.S.", ...)             // エラー：ただの String は入らない
Artist("Metallica", "Heavy Metal", Location("U.S."), ...)   // OK
Artist("Metallica", "Heavy Metal", Location("太郎"), ...)   // OK になってしまう
```

#### 中身まで制限したい時

(1) 作る時にチェックする（newtype + Option）

```scala
object model {
  opaque type Location = String

  object Location {
    private val known = Set("U.S.", "England", "Japan")

    def fromString(value: String): Option[Location] =
      if (known.contains(value)) Some(value) else None
  }
}

Location.fromString("U.S.")   // Some(U.S.)
Location.fromString("太郎")   // None
```

(2) 選択肢が決まっているなら、直和型にする

```scala
enum Country {
  case US
  case England
  case Japan
}
```

これなら「太郎」は書くことすらできない

### Rust では

要素が1つだけの構造体（タプル構造体）で同じことをする。newtype パターンと呼ばれる

```rust
struct Location(String);          // 中身は String だが、別の型

impl Location {
    fn new(value: &str) -> Location {   // 作るための関数
        Location(value.to_string())
    }
    fn name(&self) -> &str {            // 中身を取り出すための関数
        &self.0                         // .0 は「1つ目の要素」
    }
}

struct Artist {
    name: String,
    genre: String,
    origin: Location,
}
```

## 7.2 ADT：「かつ」と「または」で、矛盾した状態を作れなくする

### ゴール

要件を読んで、どこが「かつ」でどこが「または」かを分けて型にできること
→ 矛盾した組み合わせがそもそも書けなくなる

### 詳細

残る問題2つ

```scala
case class Artist(
  name: String,
  genre: String,            // 問題A：何でも入る
  origin: Location,         // 7.1で解決済み
  yearsActiveStart: Int,
  isActive: Boolean,        // 問題B：この2つが矛盾しうる
  yearsActiveEnd: Int
)
```

- 問題A：genre には "Heavy Metal"、"heavy-metal"、打ち間違いなど、どんな文字列でも入ってしまう
- 問題B：isActive = true（今も活動中）なのに yearsActiveEnd = 2010（2010年に終了）、という矛盾したデータが作れてしまう

#### 解決策：4段階で直していく

**段階1：「ないかもしれない」を Option で表す**

今も活動中なら、終了年は「ない」はず。それなのに Int で何か値を入れなければならないので、矛盾が生まれる。
そこで、終了年を Option にして、isActive は消す。

```scala
case class Artist(name: String, genre: String, origin: Location,
                  yearsActiveStart: Int, yearsActiveEnd: Option[Int])
// 終了年が None なら今も活動中、Some(1980) なら1980年に終了
```

**段階2：1つの概念を、1つの直積型にまとめる**

開始年と終了年はバラバラの項目ではなく、セットで「活動期間」という1つの概念。そこで、1つの型にまとめる

```scala
case class PeriodInYears(start: Int, end: Option[Int])
case class Artist(name: String, genre: String, origin: Location, yearsActive: PeriodInYears)
```

case class のように「全部の項目を持つ」型を直積型と言う。「開始年かつ終了年」

**段階3：有限の選択肢を、直和型で表す（問題A の解決）**

ジャンルは決まった選択肢の「どれか1つ」。そこで選択肢を列挙する。

```scala
enum MusicGenre {
  case HeavyMetal
  case Pop
  case HardRock
}
```

このように「どれか1つ」を表す型を直和型と言う。「HeavyMetal または Pop または HardRock」
列挙した以外の値は作れないので、打ち間違いも入らない。

**段階4：直和型と直積型を組み合わせる**

段階2の PeriodInYears で矛盾はなくなった。ただ、「終了年が None なら活動中」という意味は、型を見ても分からない。
そこで、活動期間を「2つの場合のどちらか」として直接書く。

```scala
enum YearsActive {
  case StillActive(since: Int)                 // 今も活動中：開始年だけ
  case ActiveBetween(start: Int, end: Int)     // 活動終了：開始年と終了年
}
```

全体の型は「2つの場合のどちらか（直和）」で、それぞれの場合の中身は「項目を全部持つ（直積）」

最終的な Artist は以下

```scala
case class Artist(
  name: String,
  genre: MusicGenre,
  origin: Location,
  yearsActive: YearsActive
)

Artist("Metallica", MusicGenre.HeavyMetal, Location("U.S."),
       YearsActive.StillActive(since = 1981))
Artist("Led Zeppelin", MusicGenre.HardRock, Location("England"),
       YearsActive.ActiveBetween(start = 1968, end = 1980))
```

直積型と直和型を組み合わせて作った型を、ADT（代数的データ型）と言う

#### 注意

ADT で防げるのは「構造の矛盾」まで。「開始年が終了年より後」のような値どうしの関係は、型だけでは防げない。
そこは7.1の「チェック付きの作成関数」で守る

### Rust では

Rust の struct が直積型、enum が直和型。
Rust の enum は、各ケースにデータを持たせられるので、Scala の enum とそのまま対応

```rust
struct Location(String);          // 7.1 の newtype

enum MusicGenre {                 // 直和型
    HeavyMetal,
    Pop,
    HardRock,
}

enum YearsActive {                // 直和型（各ケースの中身は直積）
    StillActive { since: i32 },
    ActiveBetween { start: i32, end: i32 },
}

struct Artist {                   // 直積型
    name: String,
    genre: MusicGenre,
    origin: Location,
    years_active: YearsActive,
}

let led_zeppelin = Artist {
    name: "Led Zeppelin".to_string(),
    genre: MusicGenre::HardRock,
    origin: Location("England".to_string()),
    years_active: YearsActive::ActiveBetween { start: 1968, end: 1980 },
};
```

Option（6章）も Either（6章）も直和型だった。
作った ADT の値をどう使うか（どのケースかで分岐して中身を取り出す）が、次の7.3のパターンマッチ。

## 7.3 パターンマッチ：ADT を使う関数を書く

### ゴール

- 直和型を受け取る関数を、全ケース漏れなく書ける
- 型を変えると、コンパイラが直す場所を教えてくれることが分かる（7章のゴールの「コンパイラを使って要件の問題を見つける」）

### 詳細

#### パターンマッチがやっていること

7.2で作った YearsActive は、「StillActive か ActiveBetween のどちらか」という直和型だった。
この値を使う関数は、「今どちらのケースか」で処理を分ける必要がある。それをするのがパターンマッチ。
例として、「指定した期間（yearStart〜yearEnd）に活動していたか」を判定する関数を書く。

```scala
import YearsActive._   // StillActive などを「YearsActive.」を付けずに書くため

def wasArtistActive(artist: Artist, yearStart: Int, yearEnd: Int): Boolean =
  artist.yearsActive match {
    case StillActive(since)        => since <= yearEnd
    case ActiveBetween(start, end) => start <= yearEnd && end >= yearStart
  }
```

match の受け取るもの・返すもの

- 受け取るもの：直和型の値（ここでは artist.yearsActive）
- 各 case：「パターン => そのときの式」
- 返すもの：当てはまった case の式の値（match 全体が1つの式で、if と同じように値を返す）

パターンマッチは2つの仕事を同時にしている

1. 分岐：値がどのケースかを判定する
2. 分解：そのケースの中身を取り出して名前を付ける。`StillActive(since)` と書くと、中の開始年が since という名前で使えるようになる

他の例（Int を返す例。活動年数を計算する）

```scala
def activeLength(artist: Artist, currentYear: Int): Int =
  artist.yearsActive match {
    case StillActive(since)        => currentYear - since
    case ActiveBetween(start, end) => end - start
  }
// currentYear = 2026 のとき：Led Zeppelin → 12、Metallica → 45
```

#### ケースを書き忘れると、コンパイラが教えてくれる

ActiveBetween の case を書き忘れると、Scala は「match が網羅的ではない。ActiveBetween の場合に失敗する」という警告を出す。
これが一番効いてくるのは、要件が変わって型を変えたとき。
たとえば YearsActive に新しいケースを1つ足すと、YearsActive を match している全ての関数で「このケースが処理されていない」と指摘される。
直すべき場所をコンパイラが全部列挙してくれるので、修正漏れが起きない。

#### 注意

`case _ =>`（「それ以外すべて」）と書くと、どんなケースもそこに当てはまる。便利だが、新しいケースを足しても指摘されなくなるので、直和型ではなるべく全ケースを書く方が安全

#### Option の forall / exists / contains は、パターンマッチの省略形

Option も直和型（Some か None）なので、パターンマッチで処理できる。
7.2の段階2の `PeriodInYears(start: Int, end: Option[Int])` で、よく使う形を見てみる。
ここでの省略形は全部 None の時どう扱うか

| やりたいこと | パターンマッチで書くと | 省略形 |
|---|---|---|
| 「今も活動中か、終了年が year 以降」 | `end match { case None => true; case Some(e) => e >= year }` | `end.forall(e => e >= year)` |
| 「終了年があり、それが year より前」 | `end match { case None => false; case Some(e) => e < year }` | `end.exists(e => e < year)` |
| 「終了年が1980年ちょうど」 | `end match { case None => false; case Some(e) => e == 1980 }` | `end.contains(1980)` |

3つとも、違うのは「None のときに何を返すか」と「Some のときの条件」だけ

- forall：None なら true（「全部満たす」とみなす。数学の「空集合の全称命題は真」と同じ）
- exists：None なら false（「満たすものが存在しない」）
- contains：exists の条件が「ちょうどその値と等しい」になったもの

### Rust では

Rust の match も同じだが、違いは2点。

- ケースを書き忘れると、Rust では警告ではなくコンパイルエラーになる。
- 名前付きのフィールドを持つケースは `{ }` で分解する。

```rust
enum YearsActive {
    StillActive { since: i32 },
    ActiveBetween { start: i32, end: i32 },
}

fn was_artist_active(artist: &Artist, year_start: i32, year_end: i32) -> bool {
    match artist.years_active {
        YearsActive::StillActive { since } => since <= year_end,
        YearsActive::ActiveBetween { start, end } => start <= year_end && end >= year_start,
    }
}

fn active_length(artist: &Artist, current_year: i32) -> i32 {
    match artist.years_active {
        YearsActive::StillActive { since } => current_year - since,
        YearsActive::ActiveBetween { start, end } => end - start,
    }
}
```

ActiveBetween の行を消すと、次のエラーになる

```
error[E0004]: non-exhaustive patterns: `&YearsActive::ActiveBetween { .. }` not covered
```

Option の省略形

| Scala | Rust |
|---|---|
| `end.forall(e => e >= year)` | `end.is_none_or(\|e\| e >= year)`（Rust 1.82 以降） |
| `end.exists(e => e < year)` | `end.is_some_and(\|e\| e < year)` |
| `end.contains(1980)` | `end == Some(1980)` |

### まとめ

| | Scala | Rust |
|---|---|---|
| 直和型で分岐して中身を取り出す | `match { case ... => }` | `match { ... => }` |
| ケースを書き忘れたとき | 警告 | コンパイルエラー |
| 型にケースを足したとき | match している全ての場所が指摘される | 同じ（エラーになる） |
| 「それ以外すべて」 | `case _ =>`（使いすぎ注意） | `_ =>`（同じく注意） |
| Option の判定の省略形 | `forall` / `exists` / `contains` | `is_none_or` / `is_some_and` / `== Some(v)` |

## 7.4 振る舞いもデータで表す

### ゴール

検索条件のような「何をするか」の指示を ADT で表し、それをパターンマッチで処理する関数を書ける

### 詳細

#### 出発点：引数がフラグだらけの検索関数

「ジャンル」「出身地」「活動期間」でアーティストを検索する関数を、素朴に書くと次のようになる

```scala
def searchArtists(
  artists: List[Artist],
  genres: List[MusicGenre],       // 空リストなら「ジャンルで絞り込まない」
  locations: List[Location],      // 空リストなら「出身地で絞り込まない」
  searchByActiveYears: Boolean,   // 活動期間で絞り込むかどうか
  activeAfter: Int,               // searchByActiveYears が false なら意味がない
  activeBefore: Int               // 同上
): List[Artist] = ...
```

「イギリス出身」だけで検索したいときも、使わない引数を全部埋める必要がある。これは不便。

```scala
searchArtists(artists, List.empty, List(Location("England")), false, 0, 0)
//                     ↑空なら絞り込まない          ↑false なので 0, 0 には意味がない
```

これには、7.2で Artist に対して見たのと同じ問題がある

| 問題 | 中身 |
|---|---|
| 意味のない組み合わせ | `searchByActiveYears = false` なのに年が入っている。7.2の「活動中なのに終了年がある」と同じ |
| 暗黙のルール | 「空リストなら絞り込まない」は型を見ても分からない |
| 拡張しにくい | 検索条件の種類を足すたびに、引数が増えて全ての呼び出しを直すことになる |

#### 解決策

「検索条件は、ジャンルか出身地か活動期間のどれか」なので、直和型にする。
それぞれのケースは、その条件に必要な値だけを持つ。

```scala
enum SearchCondition {
  case SearchByGenre(genres: List[MusicGenre])
  case SearchByOrigin(locations: List[Location])
  case SearchByActiveYears(start: Int, end: Int)
}
```

検索関数は「条件のリスト」を受け取り、すべての条件を満たすアーティストだけを残す

```scala
import SearchCondition._

def searchArtists(artists: List[Artist],
                  requiredConditions: List[SearchCondition]): List[Artist] =
  artists.filter(artist =>
    requiredConditions.forall(condition =>
      condition match {
        case SearchByGenre(genres)           => genres.contains(artist.genre)
        case SearchByOrigin(locations)       => locations.contains(artist.origin)
        case SearchByActiveYears(start, end) => wasArtistActive(artist, start, end)
      }
    )
  )
```

よは検索では、どの条件を使うかが毎回変わるので、条件をリストで受け取る。そうすると、役割はこう分かれる。

- 「次へ進む／終わる」：条件のリストを順にたどる forall の役目（イギリス人なら次へ進むなど、&& の考え）
- 「この条件は、どう確かめるか」：条件の種類を見て選ぶ match の役目

forall が「イギリス人か？→ 活動期間は？」と順に進み、それぞれの条件のところで、match が「この種類なら、こう確かめる」を選んでいる、という分担

呼び出す側は必要な条件だけ並べる

```scala
searchArtists(artists, List(SearchByOrigin(List(Location("England")))))
```

#### 何がうれしいのか

- 意味のない組み合わせを渡せない：活動期間で検索しないなら、SearchByActiveYears を入れないだけ。使わない引数に 0 を入れる必要はない。
- 条件を足しやすい：新しい条件（たとえば「活動年数で検索」）は、SearchCondition にケースを1つ足して、match に1行足すだけ。足し忘れれば、7.3のとおりコンパイラが場所を教えてくれる。関数の引数は変わらないので、呼び出す側を直す必要もない
- 条件そのものが値になる：リストにして並べたり、保存したり、組み合わせたりできる。

#### 関数で渡すのとの違い（4章とのつながり）

検索の条件を「関数」で渡すか、「データ（ADT）」で渡すかの比較。
どちらでも検索はできるが、データで渡すと、検索以外のこと（表示・保存・比較）にも使える

関数で渡す（4章のやり方）

```scala
searchArtists(artists, List(artist => artist.origin == Location("England")))
```

条件は「アーティストを受け取って、true / false を返す関数」

データで渡す（7章のやり方）

```scala
searchArtists(artists, List(SearchByOrigin(List(Location("England")))))
```

「何をするか」をデータ（ADT）で表し、「どうやるか」をそれを解釈する関数（パターンマッチ）に任せる、という分け方。
これは、プログラミング言語でソースコードを構文木（AST）というデータにして、インタプリタがそれを解釈するのと同じ構造。
数学の言葉で言えば、ADT が「構文」、match が「意味」を与えている。

### Rust では

検索条件と検索関数

```rust
enum SearchCondition {
    ByGenre(Vec<MusicGenre>),
    ByOrigin(Vec<Location>),
    ByActiveYears { start: i32, end: i32 },
}

fn search_artists(artists: &[Artist], conditions: Vec<SearchCondition>) -> Vec<&Artist> {
    artists
        .iter()
        .filter(|artist| {
            conditions.iter().all(|condition| match condition {
                SearchCondition::ByGenre(genres) => genres.contains(&artist.genre),
                SearchCondition::ByOrigin(locations) => locations.contains(&artist.origin),
                SearchCondition::ByActiveYears { start, end } => {
                    was_artist_active(artist, *start, *end)
                }
            })
        })
        .collect()
}
```

補足が3つ

- `all` が Scala の List の forall にあたる。空のときに true になるのも同じ。
- `*start`：condition は参照なので、取り出した start も参照（`&i32`）になる。`*` で中の値を取り出して渡している。
- conditions を参照ではなく値で受け取っている理由：戻り値の `Vec<&Artist>` は参照なので、Rust は「その参照がどの引数から来たか」を知る必要がある。Rust には「参照の引数が1つだけなら、戻り値の参照はその引数から来ている」とみなす規則がある。conditions を値で受け取って参照の引数を1つにしておけば、この規則が使えるので、追加の書き込み（ライフタイム注釈）が要らない。

### まとめ

| | フラグだらけの引数 | 検索条件を ADT にする |
|---|---|---|
| 関数の引数 | 条件の種類ごとに増える | 条件のリスト1つ |
| 使わない条件 | ダミーの値を入れる | 入れないだけ |
| 条件の種類を足す | 引数が増え、全ての呼び出しを直す | ケースを1つと match に1行。漏れはコンパイラが指摘 |
| 条件を表示・保存・比較 | できない | できる（データなので） |
